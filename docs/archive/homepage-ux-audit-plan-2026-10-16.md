# HigherLower Homepage UX Audit — Plan

**Date:** 2026-10-16  
**Phase:** Plan only. This document does not authorize implementation.  
**Owner authority:** Locked decisions D1–D22 supplied in the current owner request; these supersede corresponding open product questions in the earlier homepage Analysis and Design.  
**Evidence:** [`docs/homepage-ux-audit-analysis-2026-10-15.md`](homepage-ux-audit-analysis-2026-10-15.md:1), [`docs/homepage-ux-audit-design-2026-10-15.md`](homepage-ux-audit-design-2026-10-15.md:1), current homepage source and components, catalog source, package manifest, and supplied Home design references.  
**Plan artifact scope:** This one new Markdown file only. Future source allowlists below are prospective and are not edit authorization.

## Objective and verdict

Implement a focused, preservation-led homepage UX improvement: retain the full-screen brand hero and spacious long-form setup, but provide a direct user-activated route to the first setup section, remove unintended hero parallax, reduce the hero-to-setup gap modestly, and make default selections, state feedback, motion, and the High Scores dialog conform to the owner decisions. Preserve the existing visual identity, catalog and route behavior, setup order, count copy, real disabled semantics, and modal content. Verify responsive, keyboard, reduced-motion, and interaction behavior in bounded passes; these are verification tasks, not open product decisions.

This is not a redesign, theme project, catalog change, gameplay change, or broad accessibility refactor. Do not change any behavior that already satisfies a locked decision. No new dependency is proposed: the manifest already includes `motion`, Lucide, React, Next, and Tailwind. Reuse the current project conventions and native controls.

## Evidence-grounded baseline and constraints

- The homepage dispatches the server-projected catalog to client-owned Home setup in [`app/page.tsx`](../app/page.tsx:1). `HomeSetup` currently preselects Movies & Series only if it exists, starts with no category or mode, clears the category on domain change, and clears an incompatible mode on category change; Go requires a playable compatible category and mode. Those source behaviors conflict with D5–D6 and are planned changes, not presumed product authority ([`components/home/HomeSetup.tsx`](../components/home/HomeSetup.tsx:50), [`components/home/HomeSetup.tsx`](../components/home/HomeSetup.tsx:95), [`components/home/HomeSetup.tsx`](../components/home/HomeSetup.tsx:120)).

Empty-playable-domain handling must leave a valid, understandable state and prevent invalid Go; exact fallback behavior follows D6 and the available playable set.

### Pass 1 — Hero continuity, removal of incidental parallax, and controlled motion

- **Priority / objective:** P1. Keep the viewport-height hero while providing the approved accessible `Start Comparing ↓` CTA and a modestly reduced gap to setup; remove all hero parallax. Implement only the explicitly approved motion model: one-time wordmark → supporting copy → CTA entrance; one-time, restrained setup arrival upon CTA activation; and reduced-motion-safe targeted navigation. Avoid generic viewport-triggered reveals and scroll-linked motion.
- **Decisions/findings:** D1, D2, D3, D10, D11, D14, D18, D20, D21; H-03/H-10/H-11. D1 requires explicit activation, smooth navigation only without reduced-motion preference, no auto-scroll, and no automatic focus transfer. D2 preserves long-form character. D3 removes—not tunes or replaces—the existing parallax. D10/D20 restrict entrance order and style; D21 confines arrival feedback to the CTA destination and one-time behavior. D4’s counts remain untouched.
- **Prospective implementation allowlist:** [`components/home/HomeSetup.tsx`](../components/home/HomeSetup.tsx:1); [`app/globals.css`](../app/globals.css:1) only if existing smooth-scroll/reduced-motion global rules need a narrowly scoped adjustment. No app layout or package change. Do not change count expressions/copy in HomeSetup.
- **Dependencies:** D1–D3 and motion model are locked. First inspect current dirty source and preserve unrelated changes. Existing `motion` support and CSS reduced-motion rules are present; no dependency is needed. Confirm anchor target/IDs and CSS scroll behavior do not affect unrelated routes before changing global rules; prefer homepage-scoped behavior where feasible.
- **Responsive/accessibility/motion/performance:** CTA remains a semantic link or button with descriptive visible label, keyboard operation, visible focus, sufficient touch target, and no focus jump unless later verification demonstrates benefit. Keep hero wordmark dominant at narrow widths and short heights; anchor destination must not be hidden under header. Honor prefers-reduced-motion with direct jump and immediate/nearly immediate hero/arrival. Use short opacity plus slight upward movement and short stagger only; never block input or replay on ordinary scroll re-entry. Removing scroll transforms reduces work; no measurable performance claim without a trace.
- **Risks/regression boundaries:** Do not shrink/remove full-screen hero; do not move setup into hero, auto-scroll after selector changes, add scroll snap or reveal every section, change count copy, or replace parallax with another scroll-linked effect. Global smooth-scroll behavior can affect other routes; constrain it to the CTA if possible and verify its scope. Motion hooks/effects must not create hydration divergence or replay on scroll.
- **Verification:** Source review of anchor activation and no automatic scroll/focus; rendered desktop and narrow/short-height checks; normal-motion CTA smooth scroll versus reduced-motion direct jump; keyboard activation/focus visibility; confirm ordinary scrolling does not retrigger entrance/setup arrival. Inspect reduced-motion with browser emulation if available. Compare full hero/setup composition against desktop reference; record actual browser capabilities and do not assert unsupported viewport widths. Performance trace only if implementation creates a measured concern.
- **Exit criteria:** Hero remains full-screen; CTA uses exact copy and reaches first setup only upon activation; gap is observably modestly smaller but long-form character remains; parallax code is gone; entrance order/style/replay/reduced-motion behavior follows D10/D14/D20/D21; counts and all unrelated route behavior are unchanged.

### Pass 2 — Predictable defaults and preserved valid mode selection

- **Priority / objective:** P1. Make initial playable setup ready without redundant selection, following catalog order and without hardcoded category cases; retain valid user choices across domain/category changes.
- **Decisions/findings:** D5, D6, D17; H-04/H-07. Initially select an available domain consistent with the existing initial-domain policy (currently Movies & Series if present), first playable category for that domain in the existing projection order, and Classic. On domain change choose the first playable category of the new domain. Preserve current mode if valid; otherwise choose Classic if valid or first valid playable mode. Go is immediately enabled only when the resulting category/mode combination is actually playable. D4 keeps count behavior unchanged.
- **Prospective implementation allowlist:** [`components/home/HomeSetup.tsx`](../components/home/HomeSetup.tsx:1) only. Do not edit catalog files: their projected ordering and `playable` contract already provide the required inputs. Include `components/home/CategorySelector.tsx` only if source-level evidence shows its existing props cannot represent the planned state; no such need is currently established, so it is not presently in the allowlist.
- **Dependencies:** Pass 1’s changes are independent; this pass may proceed separately after owner approval. Confirm the default domain resolution when absent and domain with zero playable categories through current projection behavior before coding; keep no-valid-category state safe and Go disabled. Existing domain list is catalog-ordered and all current categories expose `playable`/`compatibleModes`.
- **Responsive/accessibility/motion/performance:** Keep native radios; auto-selection must not disable or obscure editing. Checked state, focus, and disabled state remain distinct. Do not auto-scroll or move focus when changing choices. If category list replacement is animated under Pass 3, it must not delay selection. No extra catalog iteration or dependency is necessary beyond deriving selection from the projected arrays.
- **Risks/regression boundaries:** Resetting a still-valid mode would violate D6; hardcoded category IDs violate D17. Category ordering must come from catalog projection, not a duplicated local order. Empty or unavailable domains must never make Go launch. Preserve route construction, domain/category IDs, and category counts.
- **Verification:** Exercise initial state, each domain change, domains with no playable categories, and category changes that preserve or invalidate selected mode. Verify selected radios and disabled Go semantics in DOM/a11y tree, and confirm Go navigation still uses the selected valid IDs. Use source-level derivation where controlled catalog variants are unavailable; do not add fixture routes/test infrastructure without separate approval.
- **Exit criteria:** When a playable combination exists, initial domain/category/Classic are selected and Go is ready. Domain changes select the first playable category in projected order. A valid user-selected mode is retained; invalid modes fall back by D6. No unplayable selection can launch. Counts/copy and catalog behavior remain unchanged.

### Pass 3 — State clarity, pointer feedback, and primary Go action

- **Priority / objective:** P2. Make selection legible beyond color, preserve distinct interaction states, and establish Go as the primary setup CTA without replacing the branded system.
- **Decisions/findings:** D7–D9, D16; H-02/H-04/H-07/H-08. Refine only where current checked/hover/focus/disabled treatments do not meet owner decisions. Increase Go text size/prominence and add restrained hover/pressed feedback. Interactive controls use appropriate cursor and meaningful pointer feedback; disabled controls remain non-clickable and do not suggest interactivity. No persistent selected animation.
- **Prospective implementation allowlist:** [`components/home/DomainSelector.tsx`](../components/home/DomainSelector.tsx:1), [`components/CategoryCard.tsx`](../components/CategoryCard.tsx:1), [`components/ModeButton.tsx`](../components/ModeButton.tsx:1), [`components/home/HomeSetup.tsx`](../components/home/HomeSetup.tsx:1); [`app/globals.css`](../app/globals.css:1) only for a specifically justified shared token/rule. The shared [`components/ui/button.tsx`](../components/ui/button.tsx:1) is not proposed: current Home controls are bespoke and D7–D9 do not justify replacement.
- **Dependencies:** Pass 2’s initial selected state supplies the visual state for default choices. Reconcile all proposed edits with pre-existing dirty diffs in CategoryCard and HomeSetup; preserve unrelated owner changes. D8’s visual increase remains within existing Go shape/brand; no new design system.
- **Responsive/accessibility/motion/performance:** Native radio semantics and actual disabled properties remain authoritative. Visible focus remains high contrast; selected status includes a non-color cue; pointer hover has keyboard-focus counterpart; pressed and disabled remain distinguishable. Ensure wrap and full-width controls remain usable from narrow phones through wide displays. Use brief state transitions only, with near-instant feedback under reduced motion. Avoid layout animation or expensive effects.
- **Risks/regression boundaries:** Do not treat hover as the only cue, change category/mode availability or route behavior, add persistent pulse/glow/bounce, or imply disabled items are clickable. Visual redesign/cardification and generic shadcn conversion remain excluded.
- **Verification:** Keyboard traverse domain/category/mode/Go; inspect checked/focus/disabled states and disabled activation; mouse/touch-pointer affordance checks; hover/pressed states with reduced-motion preference; test at narrow, laptop, desktop, and large viewport classes for wrapping, overflow, control readability, and stable visual hierarchy. Compare desktop visual changes to established dark-grid/Space Mono reference. No WCAG conformance claim without formal evaluation.
- **Exit criteria:** Distinct selected/hover/focus/pressed/disabled signals meet D7–D9; Go is the clear primary action with larger text and restrained feedback; native semantics and setup order remain intact; no visual state relies on color or persistent animation alone.

### Pass 4 — Domain-driven category replacement feedback

- **Priority / objective:** P2. Communicate that changing domain changes available categories with a short state-driven fade and slight vertical movement, optionally a very restrained stagger, without generic scroll reveals.
- **Decisions/findings:** D10, D14, D19; H-02/H-10. This motion is tied to domain change, not viewport entry. In reduced motion, replacement is immediate or near-immediate with at most minimal opacity change.
- **Prospective implementation allowlist:** [`components/home/HomeSetup.tsx`](../components/home/HomeSetup.tsx:1), [`components/home/CategorySelector.tsx`](../components/home/CategorySelector.tsx:1); [`components/CategoryCard.tsx`](../components/CategoryCard.tsx:1) only if the animation must be applied to individual cards for the optional restrained stagger. Do not include CSS or catalog source unless a narrowly justified requirement is established and approved.
- **Dependencies:** Pass 2’s domain/category selection semantics. Use existing motion library already in dependencies. Avoid per-card state changes if a container-level fade/translation communicates replacement sufficiently.
- **Responsive/accessibility/motion/performance:** Preserve semantic radiogroup and focus order while content changes. Respect focused category when domain changes; do not steal focus. Keep animation short and non-blocking, with reduced-motion path. Ensure replacing content does not create announcement noise or keyboard focus loss. Avoid animating large regions/layout geometry.
- **Risks/regression boundaries:** No large horizontal slide, carousel behavior, long sequential choreography, or animation of every section. Do not delay state updates, change selection rules, or auto-scroll. Unmount/remount behavior must not strand focus.
- **Verification:** Change domains repeatedly with keyboard and pointer; verify list updates immediately, correct default category and preserved/fallback mode remain in effect, focus remains predictable, and motion runs only on replacement. Check reduced-motion, rapid successive selections, narrow viewport, and no overflow/layout instability.
- **Exit criteria:** Category content replacement is communicated by the approved short fade/slight vertical movement (optional minimal stagger only if justified); no viewport-reentry animation; reduced-motion behavior and selection/focus semantics remain clear.

### Pass 5 — High Scores dismissal, transition, and backdrop treatment

- **Priority / objective:** P2. Add backdrop dismissal specifically to High Scores and a fast, shared open/close transition; preserve homepage selections, scroll, and opener focus.
- **Decisions/findings:** D11–D14, D16, D22; H-06. Native close and Escape continue. Backdrop click/tap closes only this modal. Use moderate dark backdrop so Home remains recognizable, without heavy blur/glass. Add backdrop fade and subtle dialog fade plus small scale or translate; ensure focus and input are immediate, and all close paths share the same closing transition. Reduced motion removes/nearly eliminates spatial movement and makes transition instant/nearly instant.
- **Prospective implementation allowlist:** [`components/HighScoresModal.tsx`](../components/HighScoresModal.tsx:1); [`components/home/HomeSetup.tsx`](../components/home/HomeSetup.tsx:1) only if needed to ensure open/close does not disturb selection or page scroll/focus. [`app/globals.css`](../app/globals.css:1) only if a narrowly scoped reduced-motion/modal rule is necessary. Do not alter High Scores records, filtering, storage, confirmation semantics, or other dialogs.
- **Dependencies:** Existing native `<dialog>` and current opener state. Before implementation, verify native dialog backdrop event target/transition lifecycle in supported Next/browser context; do not sacrifice modal semantics or focus restoration to facilitate animation. Avoid dependencies.
- **Responsive/accessibility/motion/performance:** Keep dialog scrollability and controls reachable on narrow and short-height screens. Dismissal remains keyboard and pointer accessible; backdrop receives pointer handling without becoming an unlabelled focus stop. Opening must not delay focus to close control; closing must restore opener focus after transition without a long or stuck inactive interval. Reduced motion eliminates travel. Preserve current homepage scroll and selections across all exits.
- **Risks/regression boundaries:** Do not make backdrop dismissal universal, use blur/glass, or delay Escape/close/focus return until animation completion. Avoid a close-animation race with native `dialog.close()` or state changes. Do not modify modal internals outside necessary dismiss/transition integration.
- **Verification:** Open/close via button, Escape, backdrop click and touch; test repeated rapid open/close; verify dialog semantics, immediate initial focus, focus restoration, preserved selected state and scroll position. Check backdrop darkness against reference/owner direction, modal content reachability at narrow/short dimensions, and reduced-motion no-spatial-transition behavior. Validate across available browser engines and assistive technology where available; report limits.
- **Exit criteria:** All three dismissals use the same closing treatment; backdrop dismissal applies only to High Scores; state/scroll/focus are preserved; moderate backdrop and subtle animation keep the page recognizable and interaction immediate; reduced-motion behavior is effectively instant and non-spatial.

## Risks and source/reference conflicts

1. **Earlier Analysis/Design open questions:** Their product-decision entries for hero spacing, parallax, defaults/readiness, theme, selected states, and motion are superseded where they intersect D1–D22. The Plan treats those decisions as closed and maps them to passes. The untouched source documents remain historical evidence; their text is not rewritten in this phase.
2. **Source versus locked defaults:** Source currently starts category/mode unselected and clears category on domain change; D5–D6/D17 require default playable choices and mode preservation/fallback. This is a deliberate planned behavioral difference, not a reason to reopen owner direction.
3. **Source versus parallax decision:** Dirty Home source currently includes parallax; D3 explicitly removes it. Because that file already has pre-existing user changes, future code must preserve unrelated edits and make a surgical removal only after separate implementation authorization.
4. **Reference coverage:** Desktop Figma confirms a tall Home and visual language but has no responsive target and lacks detailed interactive states. D1–D22 add authority for behavior and motion. Responsive specifics remain implementation decisions, not Figma claims.
5. **Modal lifecycle:** Current native dialog already handles close/Escape and observed focus behavior, but backdrop dismissal and animation interaction need browser-level verification. Native dialog close timing, backdrop targeting, reduced-motion behavior, and restoration must not become blocked by transitions.
6. **Catalog domains without playable categories:** Catalog projection exposes non-playable categories, and D17 requires first playable selection. If a domain has none, select no category and keep Go disabled; D6’s mode fallback applies only among valid playable modes. This is direct interpretation of the locked readiness conditions and source `playable` contract, not a request to alter catalog availability.
