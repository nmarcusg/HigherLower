# API Capabilities and Candidate-Pool Analysis

**Task type:** analysis only. This document records current repository evidence and frames future provider research. It does not approve a design, implementation, provider change, data threshold, catalog regeneration, or public availability decision.

## Executive summary

The repository has eleven semantic target categories. Nine have `productionPlayable: true` in the current availability record: movie/series rating, release date, gross revenue, game rating, peak concurrent players, game release date, number of albums, album release date, and YouTube subscribers. Two defined targets—monthly listeners and Twitch followers—are not production playable. This is a code/configuration status, not proof that all nine are currently visible or pass a fresh external/runtime check. Availability records include historical gate assertions with October 2026 evidence; they should not be restated as newly measured results. The category definitions and provider paths are recorded in [`lib/catalog/semanticCatalog.ts`](../lib/catalog/semanticCatalog.ts:73) and [`lib/catalog/availability.ts`](../lib/catalog/availability.ts:110).

The current adapters predominantly bound their candidate pools through provider popularity/activity lists, curated seeds, or bounded ranked queries. These mechanisms are signals for discovery and coverage—not verified measures of cultural recognition. The repository has no observed mechanism that measures a player's familiarity with a candidate or controls the recognizable/obscure mix of a session. Comparison values must remain semantically separate from candidate selection: a title's rating, revenue, release date, album count, or subscriber count is the game answer, not a sufficient proxy for item recognition.

**Analysis conclusion:** further category-pool work should first establish a player-centered definition and evidence for recognizability, then investigate official provider capabilities and source roles category by category. No thresholds, provider substitutions, or pool-generation changes are approved here.

## Observed architecture and readiness boundary

Semantic IDs are deliberately independent of provider names. The catalog describes metric contracts and candidate providers, but semantic compatibility does not by itself authorize production play ([`lib/catalog/semanticCatalog.ts`](../lib/catalog/semanticCatalog.ts:27)). Availability defines seven release gates: semantic identity, metric contract, server adapter, runtime evidence, route authorization, public eligibility, and reversible visibility ([`lib/catalog/availability.ts`](../lib/catalog/availability.ts:13)). Its `productionPlayable` value is an explicit release decision; actual public Home visibility is a separate projection.

Gameplay routes authorize a semantic category before calling the provider dispatcher ([`app/game/[mode]/page.tsx`](../app/game/%5Bmode%5D/page.tsx:15), [`lib/catalog/routeAuthorization.ts`](../lib/catalog/routeAuthorization.ts:45)). The dispatcher maps internal category keys to adapters/snapshot readers, filters missing names/images, rejects fewer than two items, and shuffles each returned pool ([`lib/api/index.ts`](../lib/api/index.ts:39), [`lib/api/index.ts`](../lib/api/index.ts:73)). These generic checks establish renderability and minimum count, not item quality, recognition, freshness, equitable coverage, or a suitable comparison distribution.

## Category findings

“Candidate source” means how items enter the present pool, not authority for the comparison value. “Popularity/recognizability” distinguishes a ranking or activity mechanism from demonstrated player familiarity. Strategy letters are an analytical classification for the future work: **A** bounded provider popularity/activity discovery; **B** curated/reviewed candidate pool; **C** broad or exhaustive factual metadata crawl; **D** query/topic discovery; **E** naturally bounded canonical universe. These are descriptive, not approved architecture.

### Official provider documentation research (accessed 2026-10-17)

Findings below are **Verified [official docs]** from documentation research via Exa, not live endpoint tests. Details remain subject to the separately stated open verification items.

- **TMDB:** [`Popular Movies`](https://developer.themoviedb.org/reference/movie-popular-list) is popularity ordered; [`Discover`](https://developer.themoviedb.org/reference/discover-movie) supports popularity sorting, vote-count/average filters and pagination; [`Trending`](https://developer.themoviedb.org/docs/trending) offers day/week windows. Exact pagination/schema details were not fully captured. API credentials are required; noncommercial use is free with attribution, commercial use requires contact, and the rough ~40 requests/second limit may change; honor 429 responses. Local rating implementation is popular movies with positive `voteAverage` and at least 50 votes; release-date candidates span popular movies and TV, ten pages per media; gross revenue starts from popular movies and retains positive detail revenue ([`lib/api/tmdb.ts`](../lib/api/tmdb.ts:147), [`lib/api/tmdb.ts`](../lib/api/tmdb.ts:182), [`lib/api/tmdb.ts`](../lib/api/tmdb.ts:230)). These are discovery-quality signals, not recognition evidence. No working TMDB change is proposed.
- **IGDB:** official [`Games API`](https://api-docs.igdb.com/#games) supports field selection, sorting, limits, pagination, rating-count/popularity fields, and a PopScore API. Access requires Twitch 2FA, confidential app credentials, and OAuth; noncommercial use is free, commercial use requires partnership; documented limits are 4 requests/second and 8 open requests. Exact field meanings/formulas and coverage remain unverified. Local code makes one limit-200 query sorted by `total_rating_count` and requires cover/date ([`lib/api/igdb.ts`](../lib/api/igdb.ts:44), [`lib/api/igdb.ts`](../lib/api/igdb.ts:126)).
- **Steam/SteamSpy:** SteamSpy is third-party, not Valve; no official SteamSpy endpoint docs were located. Valve's official [`Steamworks review documentation`](https://partner.steamgames.com/doc/store/reviews) describes review criteria/date ranges, but does not establish global discovery ranking or a public current concurrent-player list. Keep `ccu` as the repository's previous-day peak concurrent metric; do not conflate it with current online users. Secondary-source claims about SteamSpy top lists remain **Needs Verification [official provider research]**. Local rating query uses `top100forever` plus at least 500 reviews, sorted by review percentage; player count uses `top100in2weeks`, filters zero `ccu`, and sorts by `ccu` ([`lib/api/steamspy_ratings.ts`](../lib/api/steamspy_ratings.ts:37), [`lib/api/steamspy.ts`](../lib/api/steamspy.ts:70)).
- **Spotify/music:** official [`Development mode`](https://developer.spotify.com/documentation/web-api/concepts/quota-modes) requirements/allowlist limits changed in February 2026. [`Search`](https://developer.spotify.com/documentation/web-api/reference/search) is query matching, not documented arbitrary global popularity ranking. Popularity-field behavior changed in February and was partially reverted in the [`March changelog`](https://developer.spotify.com/documentation/web-api/references/changes); current exact availability must be checked against live schema. Spotify's [`Developer Terms`](https://developer.spotify.com/terms) restrict analyzing its content/service to create derived listenership metrics and commercial use; Spotify-derived popularity ranking is a terms/access risk and not a straightforward recommendation without clarification/approval. [`Spotify Charts`](https://charts.spotify.com/) could be explored externally, but rights, terms, scope, country and artist/album coverage, availability, and licensing need verification. Do not conflate Last.fm with Spotify. MusicBrainz/CAA remain factual identity/date/art sources, not popularity evidence unless separately established.
- **MusicBrainz:** official [API documentation](https://musicbrainz.org/doc/MusicBrainz_API) supports name search to resolve MBIDs, followed by lookup/browse by MBID; browse defaults to 25 records and permits up to 100 per page. The [rate limit](https://musicbrainz.org/doc/MusicBrainz_API/Rate_Limiting) is at most one request per second. The [data license](https://musicbrainz.org/doc/About/Data_License) distinguishes CC0 core data from supplementary CC BY-NC-SA 3.0 data; non-commercial API use is free, while commercial service is directed to plans/contact. URL relationships/external IDs can assist reconciliation, not establish familiarity or validate a candidate. These are factual identity/catalog capabilities, not popularity ranking.
- **Spotify charts and API:** official [Spotify Charts help](https://support.spotify.com/us/artists/article/understanding-spotify-charts/) documents visible daily/weekly song and album charts; it does not establish a public bulk API or reuse permission, nor an artist leaderboard or album recognizability. Web API [Search](https://developer.spotify.com/documentation/web-api/) is catalog/query matching, not documented global ranking or exhaustive traversal. Popularity-field availability remains unclear following 2026 changes. [Rate limits](https://developer.spotify.com/documentation/web-api/concepts/rate-limits), [Developer Terms](https://developer.spotify.com/terms), and [extended-access criteria](https://developer.spotify.com/documentation/web-api/concepts/quota-modes) constrain access and use. **Do not recommend persistent Spotify-derived rankings as currently permitted**; provider/legal confirmation is required. Official chart pages may be manual leads only until reuse, access, scope, and terms are verified.
- **Luminate:** official [Music API](https://luminatedata.com/api/), [Music API updates](https://docs.luminatedata.com/changelog/music-api-updates), and [chart documentation](https://support.luminatedata.com/portal/en/kb/articles/charts) describe chart owner/market/time, artist/song/album metadata, history/week ranks and metrics, weekly updates, and chart depth examples including a 200-position album chart. This is a plausible sourced chart-identity route, but requires credential/business/licensing access. Commercial rights, pricing, territory, and entity crosswalk need provider/legal verification; not an approved provider choice.
- **Wikidata and Wikipedia:** [Wikidata data access](https://www.wikidata.org/wiki/Wikidata:Data_access) provides CC0 structured identity/external IDs, not current chart ranking; WDQS is not a reliable broad fuzzy/exhaustive discovery route and request rates should be sensible. [Wikimedia Pageviews](https://wikitech.wikimedia.org/wiki/Analytics/AQS/Pageviews) represent article visits by project/time and are lagged and language/geography-biased, not streams or proof of fame. [Wikipedia notability](https://en.wikipedia.org/wiki/Wikipedia:Notability) is an editorial coverage criterion, not a popularity measure. These may support weak secondary identity screening only.
- **YouTube Charts:** official [YouTube Charts help](https://support.google.com/youtube/answer/9014376?hl=en) describes weekly top artists/songs/videos in 61 countries/regions, while [artist chart methodology](https://support.google.com/youtube/answer/7239739?hl=en) aggregates an artist's discography/video uses. User-facing charts do not demonstrate API/bulk export or reuse permission; a video-list channel need not be the artist's official channel.
- **YouTube API and terms:** official [`Search: list`](https://developers.google.com/youtube/v3/docs/search/list) is query-based, max 50 results/page, and consumes the search quota bucket (100 calls/day); indexed results can be incomplete or delayed. [`Channels: list`](https://developers.google.com/youtube/v3/docs/channels/list) can resolve known channel IDs or `forHandle` at cost 1 and retrieve statistics. [`Videos: list`](https://developers.google.com/youtube/v3/docs/videos/list) `mostPopular` is a video ranking, now Trending Music/Movies/Gaming after July 2025, not a channel leaderboard. Official [quota cost](https://developers.google.com/youtube/data/determine_quota_cost), [quota/compliance audit](https://developers.google.com/youtube/v3/guides/quota_and_compliance_audits), and [API Services Terms](https://developers.google.com/youtube/terms/api-services-terms-of-service) apply. Known canonical IDs followed by metric lookup are better supported than treating search order as familiar candidates, but no architecture or retention approval follows. Third-party scrapers/rankings remain too uncertain without provenance, compliance, and licensing review; no public global channel leaderboard was identified.

## Data flow and session-level exposure

The server route authorizes the semantic category before fetching normalized `GameItem`s, then passes the initial pool to Classic or Time Attack ([`app/game/[mode]/page.tsx`](../app/game/%5Bmode%5D/page.tsx:33)). The dispatcher shuffles after filtering only for name and image and checking a two-item minimum ([`lib/api/index.ts`](../lib/api/index.ts:103)). Deck helpers filter unusable items, shuffle on explicit restart, and avoid adjacent equal comparison values where possible; equal-value avoidance is explicitly a secondary quality guard ([`lib/game/deck.ts`](../lib/game/deck.ts:16)).

Classic advances through a pool without repeating an ID until it is consumed, then forms a new shuffled cycle; Time Attack tracks consumed IDs for its session (deck contract documented at [`lib/game/deck.ts`](../lib/game/deck.ts:16)). None of these mechanics measure or enforce recognizability, category/era/region variety, or a recognizable/obscure session mixture. Consequently, a session can receive adjacent obscure items, and a high-volume pool can still create difficult pairings. Later cycles may expose repeats across separate Classic cycles; session-long handling differs by mode. These are implications of the observed deck policy, not runtime frequency measurements.

## Candidate future evidence (not implementation requirements)

Before choosing a strategy, a future analysis/design phase could compare candidate pools against player-centered measures. The following are suggested evaluation dimensions only; no thresholds, instrumentation, or data collection is authorized by this analysis:

1. **Item familiarity:** player-reported recognition/familiarity by item, with geography, language, age cohort, and domain context where ethically and practically appropriate. For music, distinguish artist recognition from album recognition; for YouTube, capture channel type and subscriber visibility.
2. **Pair recognizability:** recognition of either item per pair and session-level recognition rate; distinguish neither/one/both recognized, a challenging pair from two unknowns, and obscure-vs-obscure frequency.
3. **Game outcome and success:** correct-guess rate and score/run completion, segmented by category and familiarity class, not interpreted alone as fun or quality.
4. **Obscure-vs-obscure exposure:** rate and placement of pairs with low recognition; inspect whether these cluster early, late, or after a long streak.
5. **Position/depth trends:** recognition and decision success by deck position/page-derived candidate cohort, including a niche-concentration/deep-position gradient, to detect truncation or worsening depth quality.
6. **Bias and coverage:** source/provider, language, geography, genre, era, franchise/creator, media format, artist/album familiarity, channel type, and hidden-subscriber exclusion; consider duplicates, freshness and inactive famous channels. Usage population and provider sampling can both bias results.
7. **Repeat exposure:** same-item recurrence within and across sessions/cycles, and whether exposure improves later recognition. Current source inspection does not establish actual repeat frequencies.

Potential candidate/factual-source role separation for later investigation:

| Role | Possible evidence, subject to verification | Boundary |
|---|---|---|
| Candidate identity/discovery | Curated/reviewed candidates; provider discovery queries; licensed or otherwise authorized catalogs | Discovery order/query count does not prove familiarity or completeness |
| Identity and factual metadata | MusicBrainz identity/release-group data, CAA art, and provider channel/title details as relevant | Factual metadata and images do not establish popularity; keep identity resolution distinct from candidate discovery |
| Gameplay metric authority | Existing approved provider metric path for each category | Do not silently substitute a different metric or change its semantics; metric magnitude is not a recognition score |
| Independent recognition evidence | Consent-based, player-centered familiarity evaluation or a clearly documented independent source | Must not be inferred from provider rank, raw metric magnitude, image availability, or a different platform's metric |
| Data-quality validation | IDs, uniqueness, image/name/date/value checks, source attribution and freshness | Technical validity is necessary but not sufficient for player suitability |
